Every change to njMule comes with tests, and every test reads as a short scenario. This page shows
the style the project requires, the tools the tests are written with, the black-box flow and corpus
tests, and what CI runs on every push.

## Tools

| Tool | Used for |
|---|---|
| `cargo test` (`njmule-engine`) | unit, integration, corpus and black-box flow tests of the Rust engine |
| `proptest` | property-based tests of codecs, parsers and protocol primitives |
| `cargo-llvm-cov` | line coverage of `njmule-engine` (at least 70% enforced in CI; LCOV uploaded to SonarQube Cloud) |
| Vitest with happy-dom | unit tests of the Vue interface (`njmule-ui`) |
| `cargo test` (`njmule-desktop/src-tauri`) | unit tests of the Tauri desktop shell |

## The given/when/then style

Every test follows the given/when/then form of Gherkin:

- Each test function has a descriptive `should_...` name stating the expected behaviour, and its
  body calls helper steps in order: `given_...` (if any), then **one** `when_...`, then one or
  more `then_...`.
- A scenario has one action. Independent cases become separate tests (or a loop over cases); the
  earlier stages of a longer flow become `given_...` steps.
- Shared state lives in a fixture struct, and a `when_...` step that can fail stores its `Result`
  for `then_...` to inspect.

An example in Rust:

```rust
#[derive(Default)]
struct Sanitizer {
    network_name: String,
    safe_name: String,
}

impl Sanitizer {
    fn given_a_name_from_the_network(&mut self, name: impl Into<String>) {
        self.network_name = name.into();
    }

    fn when_the_name_is_made_safe(&mut self) {
        self.safe_name = path_sanitizer::file_name(&self.network_name);
    }

    fn then_the_safe_name_is(&self, expected: &str) {
        assert_eq!(self.safe_name, expected);
    }

    fn then_the_safe_name_fits_the_length_limit(&self) {
        assert!(self.safe_name.len() <= 200);
    }
}

#[test]
fn should_escape_a_reserved_name_hidden_by_the_length_cut() {
    let mut test = Sanitizer::default();
    test.given_a_name_from_the_network(format!("CON{}x", " ".repeat(300)));

    test.when_the_name_is_made_safe();

    test.then_the_safe_name_is("_CON");
    test.then_the_safe_name_fits_the_length_limit();
}
```

The interface's Vitest tests follow the same form, with `given...`, `when...` and `then...`
functions inside each `describe` block.

## Running engine tests

From `njmule-engine/`:

```bash
cargo test --locked
```

The integration tests under `njmule-engine/tests/` are compiled as modules of a single test binary
(`tests/main.rs`, target name `suite`) so the engine is linked once instead of once per file.
Declare every new test file in `tests/main.rs` (`mod foo_test;`) — `suite_modules_test` fails if
any `.rs` file in `tests/` is left out. Run one module's tests with:

```bash
cargo test --locked --test suite -- tag_codec_test::
```

Tests never reach outside the machine: UPnP, default server/node lists, GitHub update checks and
DB-IP country downloads stay disabled in test configurations.

:::danger[No personal data in the repository]
Copies of a real eMule profile, captures and screenshots of your own eMule belong in the git-ignored
`fixtures-private/` folder, never in a commit.
:::

## Black-box flows and wire transcripts

`njmule-engine/tests/flow_lab.rs` provides in-process protocol doubles (`FakeServer` and `FakePeer`)
and `BlackBoxEngine`, which launches the real compiled `njmule` binary with
`NJMULE_CONTROL_ENDPOINT=1` and drives it strictly through its HTTP remote-control API and SSE event
stream (`server_flow_test.rs`, `search_flow_test.rs`, `download_flow_test.rs`).

Every packet received by `FakeServer` and `FakePeer` is recorded in a `Transcript`, masked for
per-run values (user hash, client ID, ephemeral ports, version, local addresses, random challenges,
block request ordering, router traversal flag), and compared against the recorded wire transcripts
in `njmule-engine/tests/transcripts/`. Every expected packet must arrive and every packet of a
recorded kind must match the transcript.

## Property-based, fuzz and golden corpus tests

- Codecs and parsers have `proptest` properties and mutation-fuzz tests (`mutated_messages_test.rs`)
  that mutate valid eD2K and Kad messages thousands of times to verify decoders never panic or
  overflow on hostile input.
- Independent golden vectors generated by Python scripts in `tools/golden/` live in
  `njmule-engine/tests/golden/` (`file-hashes.txt`, `obfuscation.txt`).
- JSON Lines corpora in `njmule-engine/tests/golden/` check decoder compatibility across:
  - `tag-codec.jsonl` (`tag_codec_corpus_test`)
  - `packets.jsonl` (`packet_corpus_test`)
  - `profile-files.jsonl` (`profile_files_corpus_test`)
  - `ed2k-links.jsonl` (`ed2k_link_corpus_test`)
  - `kad-keywords.jsonl` (`keywords_corpus_test`)
  - `search-expressions.jsonl` (`search_parser_corpus_test`)
  - `hashes.jsonl` (`hash_corpus_test`)

## Interface tests

The interface's tests live in `njmule-ui/src/__tests__/*.test.ts` and run with Vitest on happy-dom
against the TypeScript types generated from `njmule-engine/assets/openapi.yaml`:

```bash
cargo xtask ui
```

In `njmule-ui/`, `npm run test` runs Vitest directly. See [Interface](interface.mdx).

## Desktop window tests

The desktop shell has Rust unit tests beside its code in `njmule-desktop/src-tauri/src`: eD2K link
handoff, launch options, window placement, saved remote connections, and installer/update commands.
Run them in `njmule-desktop/src-tauri/` once `cargo xtask ui-site` has built the interface:

```bash
cargo test --locked --release
```

Before packing, the release workflow also runs `.github/scripts/desktop-smoke-test.ps1` or
`desktop-smoke-test.sh`: the window prints its version, starts the `njmule` engine beside it on a
temporary profile, verifies the control endpoint starts, and shuts the engine down cleanly when
closed.

## Pictures of the interface

This site's screenshots are captured from the real Vue interface served by the Rust demo example
`njmule-engine/examples/web_capture_demo.rs`, which starts an offline engine with synthetic example
data (free files and RFC 5737 documentation addresses only). `website/scripts/capture-web.mjs`
drives the installed Chrome or Edge through Playwright and captures every screen, menu and dialog in
light, dark and forced-colours (high contrast) modes:

```bash
cargo xtask site-prepare
```

The images land in `website/build/web-captures/`. See [Documentation](documentation.mdx#screenshots).

## Continuous integration

The `Build` workflow (`.github/workflows/build.yml`) runs on every push to `main`, on every pull
request, and once a week on everything:

| Job | What it does |
|---|---|
| `interface (ui)` | `cargo xtask ui` (API types, `vue-tsc`, Vite, Vitest, Prettier, assets) |
| `desktop shell` | on Ubuntu, Windows and macOS: `cargo xtask ui-site`, then `cargo fmt --check`, Clippy (`-D warnings`) and `cargo test --locked --release` |
| `rust engine + SonarQube Cloud` | on Ubuntu: `xtask` checks, then `njmule-engine` `cargo fmt --check`, Clippy (`-D warnings`), `cargo llvm-cov --locked` (≥ 70% lines + LCOV), `cargo-deny`, `cargo-about` (`THIRD-PARTY.txt`), `cargo-cyclonedx` (SBOM), and SonarQube Cloud analysis |
| `engine (windows-x64)` | builds `ui-compress`, `native-service` and `njmule.exe` in release mode, smoke-tests `--version`/`--license`, and runs the real Windows service install/start/stop/uninstall test |
| `engine (macos-arm64)` | builds `ui-compress` and `njmule` in release mode, and smoke-tests `--version`/`--license` |
| `synology package (x86_64)` | builds the static musl `njmule` executable, verifies `ldd` reports no dynamic libraries, smoke-tests it, and builds and verifies the `.spk` package |
| `REUSE compliance` | `reuse lint` across the repository |
| `actionlint` | lints GitHub Actions workflows when they change |
| `CI result` | the single required branch check: passes when every job passed or was skipped |

Each job uses path filters so documentation-only changes skip unaffected build jobs. The website has
its own workflow ([Documentation](documentation.mdx#deployment)).
