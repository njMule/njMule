---
title: Benchmarks
description: How to measure the performance of njMule's Rust engine in release builds - hashing speed, profiling hot paths and measuring changes before and after.
---

Because njMule compiles directly to native Rust executables, always measure performance on a
**release** build (`--release`), never a debug build, and compare before and after on the same
machine.

## Hashing speed

Hashing large shared files is the most CPU- and disk-intensive offline work njMule performs
(computing the eD2K MD4 part hash set and the AICH SHA-1 tree in one pass). You can time it directly
with the built-in `--hash` command on a release binary:

```bash
cargo build --manifest-path njmule-engine/Cargo.toml --locked --release --bin njmule
njmule-engine/target/release/njmule --hash /path/to/large-file.iso
```

## Profiling hot paths

The release profile strips symbols by default (`strip = "symbols"` in `njmule-engine/Cargo.toml`).
To profile CPU hot paths (such as RC4 obfuscation, zlib block compression, IP filter lookups or
Kad/eD2K packet codecs) with `perf`, Instruments or `cargo-flamegraph`, enable debug info temporarily
with Cargo's config override:

```bash
CARGO_PROFILE_RELEASE_DEBUG=true CARGO_PROFILE_RELEASE_STRIP=none \
    cargo build --manifest-path njmule-engine/Cargo.toml --locked --release --bin njmule
```

When replacing a crate with hand-written code (or vice versa) for performance, measure both
implementations on the same release build and record the numbers in the commit message.
