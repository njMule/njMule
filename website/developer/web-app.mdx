njMule's web interface is a browser app written in Vue 3, Element Plus and TypeScript, in the
`njmule-webapp` project. Gradle builds it with Vite and puts it into the jar of `njmule-webui`, whose
Jetty server serves it behind the login page. The app itself holds no engine logic: it calls the
[remote-control API](api/index.mdx) with the login session and shows what it answers.

<Screenshot id="web-transfers" alt="The web interface in a browser: a sidebar with Transfers, Search, Shared Files, Messages, Network, Statistics and Options, and the list of downloads with their progress, speed, sources and status." caption="The web app, on the capture tour's example data." />

## Stack and layout

| Part | What it uses |
|---|---|
| Framework | Vue 3 with Vue Router (routes after the `#`, so the page stays at whatever address a reverse proxy gives it) |
| Components | Element Plus, themed with the desktop app's Nord colours |
| Language | TypeScript in strict mode, checked by `vue-tsc` |
| Bundler | Vite, with relative paths everywhere (`base: './'`) |
| Tests | Vitest on happy-dom |
| Formatting | Prettier |

The sources are in `njmule-webapp/src`:

| Path | Content |
|---|---|
| `main.ts`, `App.vue`, `router.ts` | the start, the frame (sidebar, top bar) and the routes of the places |
| `screens/` | one component per place: transfers, search, shared files, messages, network, statistics, settings |
| `components/` | dialogs and panels shared by the screens |
| `api.ts` | the calls to the remote-control API |
| `engine.ts`, `notices.ts`, `chats.ts` | the engine's state, the notices of finished downloads and new messages, the chats |
| `i18n.ts` | the languages and the texts |
| `icons.ts` | the line icons |
| `role.ts` | what a guest may open |
| `theme.css`, `theme.ts` | the colour tokens, light and dark |
| `__tests__/` | the Vitest tests |

## How Gradle builds it

Gradle downloads the pinned Node.js, checks it against its SHA-256, and runs `npm ci` from
`package-lock.json` without running any package's install scripts
([Dependencies](dependencies.mdx#web-app-and-site-packages)). Then:

| Task | What it does |
|---|---|
| `:njmule-webapp:bundle` | checks the types (`vue-tsc`) and bundles the app with Vite into `build/dist`, with `THIRD-PARTY.md`, the licenses of every bundled package |
| `:njmule-webapp:translations` | converts the desktop app's translations the app uses into one JSON file per language, `build/translations/i18n/<tag>.json` |
| `:njmule-webapp:flags` | copies the desktop app's country flags, which the web interface serves too |
| `:njmule-webapp:compress` | gzips the text files (JavaScript, CSS, SVG, JSON, Markdown) at the highest level into `build/shipped`; the page itself stays as it is, since the server fills it in |
| `:njmule-webapp:unitTest` | runs the Vitest tests (`npm run test`) |
| `:njmule-webapp:formatCheck` | checks the Prettier formatting (`npm run lint`) |

`assemble` runs `compress`, and `check` runs `unitTest` and `formatCheck`, so `./gradlew build`
covers them all. `njmule-webui` takes the result of `compress` into its jar, under
`org/njmule/webui/app`.

The web interface reads those files once and keeps them. It sends the gzipped files as they are to
browsers that accept gzip and unpacks them for any client that does not. For each session it fills
two `meta` tags into the page: `njmule-csrf`, the session's form token, and `njmule-role`, which is
`guest` for a guest.

## Formatting and types

Format the sources with Prettier before you commit, from `njmule-webapp`:

```bash
npm run format
```

Use the Node.js Gradle downloaded (`njmule-webapp/.gradle/nodejs/node-v…/`, with `npm` inside) or
your own Node.js 24 or newer. Prettier writes 120 columns, 4 spaces, single quotes and LF line
endings. The TypeScript configuration is strict, with `noUncheckedIndexedAccess` and no unused
locals or parameters: `./gradlew :njmule-webapp:bundle` reports what `vue-tsc` finds.

## Talking to the API

`src/api.ts` is the only door to the engine:

- Every call goes to `api/v1/…`, relative to the page, with the session cookie (`same-origin`).
- Every change (any method but `GET`) carries the session's token from the `njmule-csrf` meta tag in
  the `X-NjMule-CSRF` header, which no page of another site can send. An expired token answers 403:
  the user reloads the page.
- A 401 answer means the session ended: the app goes back to the login page.
- An error answer's `error` field becomes an `ApiError` whose message is meant for the user.

The app needs no API token: the web interface lets a logged-in session call the API whether or not
the token API (`--webui-api`) is on. The state of the engine is read once a second for the top bar
(`engine.ts`), and each screen polls what it shows while it is open (`usePoll`). The notices follow
the engine's events as server-sent events, through
`api/v1/events?types=download.completed,message.received,preferences.changed`; the browser
reconnects by itself.

## Texts and languages

The web app has no translations of its own: it uses the desktop app's keys, `t('IDS_…')` for the
texts taken from eMule and `t('nj.…')` for njMule's own ([Translations](translations.mdx)).

- The `translations` task scans the `.ts` and `.vue` files for **literal keys** in quotes and keeps
  only those in the JSON files. A key built at run time (`t('nj.mode.' + mode)`) is not found: write
  every key in full somewhere in the sources, as `settings.ts` does in its tables.
- An unknown key shows itself in brackets, `[nj.some.key]`, so that it is noticed.
- The texts keep the desktop app's Java placeholders (`%s`, `%d`, `%.1f`, `%1$s`, `%%`), which
  `format()` in `i18n.ts` fills in.
- The language is the best match of the browser's languages among `LANGUAGES` in `i18n.ts`, with
  English as the fallback of every text. Arabic, Persian and Hebrew set the page right to left.

## Icons

`src/icons.ts` holds the desktop app's line icons as SVG path data on a 24 by 24 grid, drawn with a
round 1.75 stroke; an icon marked `filled` is painted instead, and one marked `directional` is
mirrored in right-to-left languages. Use them through the `NjIcon` component. They are the desktop
app's own icons: change both together. This site draws the same file with a component of its own.

## Colours

The only colour literals of the app are in `src/theme.css`: Nord light and dark laid over Element
Plus's variables, with njMule's `--nj-*` tokens. Components use the `--el-*` and `--nj-*` variables
only; the rules are those of the desktop app ([Code style](code-style.mdx#ui-colours)).

## The guest role

The web interface can have a second password, for guests who may only look
([Guest access](/docs/web/guest)). A guest's page has `njmule-role` set to `guest`, and:

- the app opens only the transfers, the searches, the network (without the log) and the
  statistics (`GUEST_PLACES` in `role.ts`), and leaves out every control that changes something;
- the server enforces it whatever the app does: a guest's API calls may only read the transfers,
  the searches made, the servers, Kad and the statistics, and follow the events of the engine's
  start and stop, servers, searches, downloads and disk space.

<Screenshot id="web-guest" alt="The web interface as a guest sees it: a sidebar with only Transfers, Search, Network and Statistics, a Guest badge in the top bar, and the downloads without buttons that change them." caption="A guest's page: fewer places, no controls that change anything." />

When you add a screen or a control, decide what a guest sees, and keep the server's list in
`RemoteApi` (`njmule-core`) in step with `role.ts`.

## Working on the app

The page needs the server: it fills in the session's token and role, and serves the API. There is
no Vite development server; run the web interface from the build instead.

**On example data.** The capture tour's example data, which also makes this site's pictures, runs
in a web interface of its own, with no network and nothing of your profile:

```bash
./gradlew :njmule-gui:webCaptureArgs
java @njmule-gui/build/web-capture/java.args
```

The first command builds everything the app needs and writes the arguments file; run the second
with a Java 25 `java` (the one `njmule-gui/build/web-capture/launcher.json` names, for example). It
prints one line of JSON with the address, the password and the guest password, then serves until
its standard input closes: press <kbd>Ctrl</kbd>+<kbd>D</kbd> (on Windows
<kbd>Ctrl</kbd>+<kbd>Z</kbd> then <kbd>Enter</kbd>). Run both commands again after each change.

**With a real engine.** Start the headless engine with a password file and a profile of its own,
then open `http://localhost:4711/`:

```bash
./gradlew :njmule-app:run --args="--config-dir /home/you/njmule-dev --webui-password-file /home/you/njmule-dev/password.txt"
```

This engine connects to the eD2K and Kad networks like any njMule.
