Every dependency njMule uses is pinned, locked and verified. This page explains where versions live,
which libraries are welcome, how `cargo-deny` and Gradle verification guard them, and the steps
after changing a version.

## Choosing a library

- **Standard library first, then a well-known crate or package.** Before writing a utility, codec,
  parser or data structure, check whether the standard library or a maintained open-source library
  already provides it. Write your own only for what is specific to eD2K and Kad, or when nothing
  suitable exists or fits the constraints below, and say why in a comment or the commit message.
- **A license compatible with the GPL 3.0**: MIT, BSD, Apache-2.0, LGPL, GPL-2.0-or-later and the
  like. See [Licenses](#licenses) below.
- **Always the latest stable version.** Check crates.io, npm or Maven Central before adding or
  bumping a dependency.

## Rust crates

Both the engine (`njmule-engine`) and the desktop shell (`njmule-desktop/src-tauri`) are Cargo
crates:

- Rust itself is pinned in each crate's `rust-toolchain.toml`, which `rustup` installs on first use
  with `rustfmt` and Clippy.
- Dependencies are listed in `Cargo.toml` and locked with checksums in `Cargo.lock`; CI always runs
  Cargo with `--locked`.
- In `njmule-engine`, [`deny.toml`](https://github.com/njMule/njMule/blob/main/njmule-engine/deny.toml)
  enforces allowed licences, checks the RustSec advisory database, blocks unknown registries/git
  sources and bans disallowed crates. CI runs `cargo-deny` on every engine change.
- After adding or updating a crate, run `cargo update` as needed, run `cargo deny check` in
  `njmule-engine`, and commit `Cargo.toml` and `Cargo.lock` together.

## npm packages

The interface (`njmule-ui`), the desktop window's Tauri CLI (`njmule-desktop`) and this site
(`website`) are npm projects inside the Gradle build. Gradle downloads the pinned Node.js and runs
`npm ci`, which installs exactly what `package-lock.json` holds. Their `.npmrc` files set:

| Setting | Effect |
|---|---|
| `ignore-scripts=true` | no package runs code while it is installed |
| `save-exact=true` | `npm install <package>` writes an exact version, never a range |
| `engine-strict=true` | npm refuses a Node.js older than the `engines` field asks (24 or newer) |
| `audit=false`, `fund=false` | no audit or funding requests while installing |

To add or update a package, run npm in that folder (with the Node.js Gradle downloaded into its
`.gradle/nodejs` folder, or your own Node.js 24 or newer), then commit `package.json` and
`package-lock.json` together. A task that runs `npm ci` empties `node_modules` first: stop a Vite
development server before running one.

## Gradle tools and Node.js

[`gradle/libs.versions.toml`](https://github.com/njMule/njMule/blob/main/gradle/libs.versions.toml)
pins the few Gradle-managed tools: the Node.js LTS version (`nodejs`), JSVG for `tools/IconGen.java`
(`jsvg`), and the Node Gradle plugin (`node`). Gradle itself is pinned in
`gradle/wrapper/gradle-wrapper.properties` with its distribution SHA-256.

Two mechanisms ensure reproducible Gradle downloads:

- **Dependency locking**: resolved versions are written to `gradle.lockfile`,
  `buildscript-gradle.lockfile` and `settings-gradle.lockfile`.
- **Dependency verification**: every downloaded artifact, POM, module metadata and Node.js archive
  for all five platforms (Windows x64, Linux x64 and arm64, macOS x64 and arm64) is checked against
  its SHA-256 in
  [`gradle/verification-metadata.xml`](https://github.com/njMule/njMule/blob/main/gradle/verification-metadata.xml).

### After changing a Gradle or Node.js version

1. Rewrite the lock files and checksums in one run:

   ```bash
   ./gradlew --no-configuration-cache --refresh-dependencies --write-verification-metadata sha256 \
       --write-locks :iconTools :njmule-ui:nodeSetup :njmule-desktop:nodeSetup :website:nodeSetup
   ```

2. Remove stale entries from `gradle/verification-metadata.xml`.
3. Review the new checksums before committing them.
4. After changing `nodejs`, add all five platform archives to `gradle/verification-metadata.xml`
   using the checksums from Node.js's `SHASUMS256.txt`.

:::warning[Why refresh the dependencies]
Without `--refresh-dependencies`, Gradle omits parent POMs already in your local cache. Your local
build still passes, while CI starts with an empty cache and fails on missing checksums.
:::

Dependabot pull requests for Gradle change versions without running these steps: run the command on
the PR branch, commit the updated lock files and metadata, and merge once checks pass.

## Dependabot

[`.github/dependabot.yml`](https://github.com/njMule/njMule/blob/main/.github/dependabot.yml) looks
for updates once a week:

| Ecosystem | Where | Commit prefix |
|---|---|---|
| Cargo | `njmule-engine/Cargo.lock` | `chore(deps)` |
| Cargo | `njmule-desktop/src-tauri/Cargo.lock`, with the Tauri crates grouped | `chore(deps)` |
| npm | `njmule-ui/package-lock.json`, with Vue, TanStack and Vite/Vitest grouped | `chore(deps)` |
| npm | `njmule-desktop/package-lock.json`, the Tauri command line | `chore(deps)` |
| npm | `website/package-lock.json`, with Docusaurus and OpenAPI docs packages grouped | `docs(deps)` |
| Gradle | the root build and `gradle/libs.versions.toml` | `chore(deps)` |
| GitHub Actions | the workflows, whose actions are pinned by commit hash | `ci(deps)` |
| Docker | the base images of `packaging/docker`, pinned by digest | `build(deps)` |

Downloads made outside Gradle and Cargo (such as `nfpm` in `release.yml`) are also pinned by
version and verified against their SHA-256 checksums.

## Licenses

njMule is licensed under the GPL 3.0 or later, so everything it ships must be compatible with it.
When you add third-party code or an asset:

- keep its original notices;
- record its origin and license in
  [`REUSE.toml`](https://github.com/njMule/njMule/blob/main/REUSE.toml) when the file cannot carry
  an SPDX header itself, and add its license text to `LICENSES/`;
- add it to [`NOTICE`](https://github.com/njMule/njMule/blob/main/NOTICE) if it is part of the
  binary distributions.

The full lists with versions are generated automatically:

- `THIRD-PARTY.txt`: `cargo about generate about.hbs -o target/THIRD-PARTY.txt` in `njmule-engine`
- CycloneDX SBOM: `cargo cyclonedx --format json --spec-version 1.6 --describe binaries --no-build-deps --target all` in `njmule-engine`
- Interface `THIRD-PARTY.md`: generated by Vite during `:njmule-ui:bundle` and served at
  `/THIRD-PARTY.md`

Test-only libraries and build tools are not distributed.
